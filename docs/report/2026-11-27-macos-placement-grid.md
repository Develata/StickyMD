# macOS 上的位置确认：整数点取整与 0 像素容差（2026-11-27）

## 结论

**macOS 在缩放为 2 时，凡是落在奇数物理像素上的窗口位置，确认都会失败。** 每次失败都会弹出提醒“窗口未能到达目标位置（Failed）。”。
`v0.3.0` 的候选（R = `319246e`）因此没有通过 macOS 门的 P16-W10。

根因是两条规则相冲突：
- `04` #window-action-receipts 要求读回的外框与目标逐边相差不超过 `PLACEMENT_TOLERANCE_PX`，现值为 0；
- AppKit 只把窗口原点放在整数点上。

修复要动共享层：目标由共享层计算，比较也在共享层，macOS 宿主单独无法修好。因此 Windows 的构建输入指纹会变，两个平台都要在新的 R 上重建。

建议采用方案 A：由宿主报告它的外框网格，容差随网格放宽到“少于一格”。Windows 的网格为 1，判定不变。这是对 `04` 的契约改动，等 USER 批准。

## 事实

**场景：** 在 `mac-test`（macOS 27.2，1024×768 点，缩放 2）中运行候选 `319246e` 的 `mac-gui`。
- P16-W10（光标闪烁）为 FAIL：观察期间多呈现了一帧，并缺了一次光标翻转（半周期 983 ms）。
- 证据在 ignored 的 `dist/evidence/mac-vm-2026-11-27-R/gui/`，`mac-gui.json` 的 SHA-256 为 `a4e4da82…`。
- 只跑 W10 两次（`diag-w10-1`、`diag-w10-2`），空闲期间都多呈现了一帧，第 2 次又测得 930 ms 的半周期。

**多出来的那一帧：** 虚拟机中启动 6.5 秒时的截图显示，窗口底部有提示条“窗口未能到达目标位置（Failed）。”。它是一条提醒，5 秒后到期，到期时的重绘就是那一帧。

**位置确认为何失败：** 在 `319246e` 上临时给 `window_runtime.rs` 的 `apply_frame`、`observe_placement` 与 macOS 的 `set_frame` 加日志，构建后在虚拟机中运行。
这个构建只用于诊断，没有提交，worktree 已回收。

| 启动方式 | 目标（物理像素） | 向 AppKit 请求的原点（点） | AppKit 实际的原点（点） | 读回（物理像素） |
| --- | --- | --- | --- | --- |
| 没有 `config.toml` | `y=61`，高 1360 | `y=57.5` | `y=57.0` | `y=62` |
| `mac-gui` 的夹具配置（520×480 DIP） | `y=161`，高 960 | `y=207.5` | `y=207.0` | `y=162` |

- 屏幕为 1024×768 点，可见区域上边在 30 点处。
- 第二行的窗口在屏幕中部，与菜单栏无关。
- 两次都是：请求半点，AppKit 落到整数点，读回比目标多 1 个物理像素；三次读回都一样，到 500 ms 截止时判 `Failed`。
- 宽、高与 x 都是偶数像素，所以都相符。

**结论：** 缩放为 2 时，奇数物理像素的位置无法表示。目标是按比例算出来的，算出奇数像素很常见。

**影响范围：**
- 凡是这样算出的目标都会失败：启动时的显示，以及按比例算出位置的其他定位。拖动结束时以观察值为目标，不受影响。
- 是否出现，取决于显示器尺寸与位置比例，并不是每台机器每次启动都有。
- 0.2.0 已经有这项确认；macOS 的 0.2.0 本机构建很可能同样失败，但没有验证。Phase 17 的提示条让它变得可见，并在到期时多呈现一帧。

## 方案

| | A：容差随宿主的外框网格（建议） | B：目标对齐到宿主网格 |
| --- | --- | --- |
| 做法 | 宿主在 `FrameFact` 中报告外框所在的网格（物理像素）：Windows 为 1，macOS 为窗口的 backing scale（取整）。确认改为逐边 `abs_diff <= PLACEMENT_TOLERANCE_PX + 网格 - 1` | 宿主报告网格；共享层在请求之前，把目标的 x、y、宽、高对齐到网格的整数倍，比较仍是 0 容差 |
| 改动 | `stickymd-app` 的 `FrameFact` 与 `within_tolerance`；两个宿主的 `observe_frame`；`04` 第 352 行 | `stickymd-app` 的几何（所有请求定位的路径）；两个宿主报告网格；`04` 的定位条款 |
| Windows | 网格为 1，判定与今天逐字相同 | 网格为 1，目标不变 |
| macOS | 能确认 1 像素以内的偏差。拖动结束记的是观察值，按要求的位置提交时记的是要求值，都不受影响 | 目标先对齐，窗口落在要求的位置上；位置的取整由共享层决定 |
| 风险 | 小：只放宽比较 | 较大：动到所有定位路径的目标计算，并要重新核对动画与贴边条的几何 |

两种方案都改共享 crate，所以两个平台的构建输入指纹都会变：Windows 候选要重建，并在新的 R 上资格化（Windows 会话本来就还没开始）。

**坏样本**：一个按 2 像素网格回答的假宿主。目标为奇数像素、读回多 1 像素时，在修复之前判为失败。另有两条反样本：读回差 2 像素仍失败；网格为 1 时判定不变。

## 对 `v0.3.0` 发布的影响

- **R `319246e` 作废：** 它的两个候选（macOS run `45834084094`，Windows run `45834091340`）都不再使用，任何 Windows 会话都不应开始资格化它。
- **之后的步骤：** 修复合入 `main` 得到新的 R；对新的 R 重新触发两个候选构建，晋升 macOS、在 R 上跑源码测试、重做虚拟机运行。
- **已完成而未登记的三份证据：** `gui/`，以及 W10 的两次诊断运行 `diag-w10-1`、`diag-w10-2`。它们绑定已作废的候选字节，登记与否不影响新候选，由 USER 决定。

## USER 决定（2026-11-27）

- 采用方案 A：宿主报告外框网格，确认容差为 `PLACEMENT_TOLERANCE_PX + 网格 - 1`。
- 已作废候选上那三份已跑完的虚拟机证据只保留文件、不登记进账本：
  - `dist/evidence/mac-vm-2026-11-27-R/gui/`（完整 `mac-gui`）；
  - `diag-w10-1/`、`diag-w10-2/`（只跑 W10 的诊断）。

  它们绑定的字节不会再用，账本不改。

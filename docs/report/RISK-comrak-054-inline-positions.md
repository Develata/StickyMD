# RISK：Comrak 0.54 的行内位置不可信（2026-11-12）

## 结论

plan 07 的 `$` 按钮假设“Comrak 识别出的公式节点能定位到源码”。在 Comrak 0.54 上，这个假设在两种情况下不成立：

1. **结束列错误。** 多行的行内节点，如果从所在块的第二行起开始，且各行缩进不同，结束列会算错。
2. **整段位置上移。** 段首有链接引用定义（`[x]: url "标题"`）时，该段内所有行内位置都会上移被删掉的行数。

第 1 种已能绕开：多行公式的结束位置改从所报结束行上找 closer。

第 2 种影响**两步**：

- 新的等号连接（第一步）会被骗去改引用标题。
- HEAD 已有的分隔符转换（第二步）本来就会转换错位置。这一项 Windows 与 macOS 都有。

“先连接、后转换”的新顺序，让第二步的这个旧缺陷在更多输入上可以触发。

上游 `v1.0.0-rc.1` 已修好第 2 种（见下）；`v0.56` 起已修好第 1 种。

## 现象（本机复现，2026-11-12）

除注明的以外，输入都经完整按钮流程（`crates/stickymd-app/src/flow/editor.rs` 的 `convert_math_delimiters`）点击一次。

| 输入 | HEAD `baecb0a` | 当前未提交补丁 |
| --- | --- | --- |
| `[x]: u "\(a\)"\n12345678\(c\)` | `[x]: u "$a$"\n12345678\(c\)`：改了标题，真正的 `\(c\)` 没转 | 相同 |
| `foo\n=\n[x]: u "\(abc\)"\n12345678$$c\n=\nd$$` | 标题不变，`$$c=d$$` | 标题被改成 `$abc$` |
| `[x]: u "$a\n=\nb$"\n12345678$a\n=\nb$` | 不变 | `[x]: u "$a=b$"\n12345678$a\n=\nb$`：标题里的公式被连接，真正的公式没动 |

第一行是 HEAD 已有的缺陷。后两行是新顺序带来的新路径。

## 根因

- **整段上移。** 在 Comrak 0.54 中，`resolve_reference_link_definitions`（`src/parser/mod.rs` 约第 2083 行）从段落内容开头删掉引用定义，但没有调整段落的 `sourcepos.start.line` 和 `line_offsets`。随后 `parse_inlines` 仍从原起始行开始计数，所以该段所有行内节点的位置都上移了被删的行数，列号也按错误的行算。
  - 上游 `v1.0.0-rc.1` 的同名函数已在删除后执行 `lines.offsets.drain(..consumed_lines)`，并把 `sourcepos.start` 设为 `start_line + consumed_lines`（`src/parser/mod.rs` 约第 2400–2445 行）。
- **结束列。** `adjust_node_newlines` 用相对节点起始行的序号去查父块的 `parent_line_offsets`，上游已在 [kivikakk/comrak#855](https://github.com/kivikakk/comrak/pull/855) 修复（`v0.56.0`）。

## 已尝试

三轮 codex 审查（报告 [2026-11-12-math-button-equals-first.md](2026-11-12-math-button-equals-first.md)）逐步加了以下检查：

- 多行公式的结束取自所报结束行上的 closer；
- opener 须位于所报起始行，且与节点类型相符；
- 范围内除 ASCII 空白外，须恰为节点内容；
- 表格整体保护；
- 结果仍会变时拒绝。

前两轮的具体反例都已修好。但内容相同的重复公式能通过以上全部检查（第 3 轮第 1 项）。第二步是 HEAD 代码，第一步的任何检查都管不到它（第 3 轮第 2 项与上表第二行）。

## 识别判据（探针数据）

段落被整段上移时，其行内节点的最大结束行会早于段落的结束行。Setext 标题的内容应止于下划线的上一行，对它按这一点判断。

| 输入 | 关闭 Setext | 打开 Setext |
| --- | --- | --- |
| `[x]: u "t"\n12345678$$c\n=\nd$$` | 段落 1–4，行内最大结束行 3 → 判为上移 | 标题 1–3，行内最大结束行 1（应为 2）→ 判为上移 |
| `[x]: u "t"\nbar\n===` | 段落 1–3，3 → 上移 | 标题 1–3，1（应为 2）→ 上移 |
| 普通段落、行尾空格、硬换行、无结尾换行、列表、lazy 引用块 | 均相等，不误报 | 均相等，不误报 |

`foo\n=\n[x]: …` 在关闭 Setext 时是一个正常段落（1–6，6），只有打开 Setext 的解析才把它切成引用定义段。所以识别必须在第二步解析的地方也做；只在第一步做不够。

## 对规格的影响

- 采用 A：plan 07 要写明“位置不可信的段落不处理，两步都适用”。
- 采用 B：plan 07 要写明这项已知限制。
- 采用 C 或 D：本补丁不进入 plan。

另外，下面这些 plan 07 文字是在 USER 批准的文本之外，于审查中加入的，需要一并确认：

1. 紧贴另一个 `$` 的 `$...$` 不连接，用来保留现有断言 `\$$a\n=\nb$$`。
2. 第一步的扫描使用 Preview 的 Markdown 方言；表格内不连接等号行，整张表格按行保护。
3. Comrak 位置须与节点一致：
   - opener 须在所报起始行上，且与节点类型相符；
   - 范围内除空白外须恰为节点内容；
   - 多行公式的结束位置取自所报结束行。
4. 两步结果仍会被按钮再次改变时，整个 action 不做改动。例如 `$$a\n=\nc \[b\]`：HEAD 给出 `$$a=c $$b$$`，现在是不改动。

## Resolution：USER 选择方案 A（2026-11-12）

USER 选择“A 两步都保守拒绝”，并接受上文列出的 plan 07 新增规则。已实现：

- 判据只有一处：`crates/stickymd-render/src/preview/source_map.rs` 的 `inlines_shifted`。它直接比较 Comrak 报告的行号：段落里行内节点的最大结束行早于段落结束行，或 Setext 标题里早于下划线的上一行，就算上移。行号不受列号错误的影响。
- 第一步（`crates/stickymd-render/src/math_text.rs`）：关闭 Setext 的扫描中，上移的段落按整行保护，其中节点一概不定位。
- 第二步（`crates/stickymd-render/src/preview/semantic_conversion.rs`）：`PreviewParser` 在同一次 Comrak 解析里，用 `shifted_block_spans` 求出上移块的整行范围，存入 `OwnedDocumentTree::shifted_blocks`。起点落在其中的公式不转换。
- 两步都只在源码含 `]:` 时做这项检查：不含 `]:` 的源码不可能有引用定义。
- plan 07 写明了这条规则与重新评估条件（升级到修复版本后）。

这一改动让 HEAD 已有的错误转换（上表第一行）不再发生。Windows 上的行为在以下两类输入上改变，需要 Windows 回归：

- 段首有引用定义的段落；
- 文中含 `]:` 时，结尾是跨行链接的段落。

codex 第 4 轮指出了早先实现的两个问题，现已改掉：

- **字节反推行差会被绕过。** 早先第二步用最后一个行内节点的字节位置去反推行差。错位的列号能越过换行，这个判断就被绕过了，例如 `[x]: u "\(a\)"\n12345678\(c\) tail`。
- **没有字节位置的节点会造成误判。** 后面有无法映射成字节范围的节点时，会把正常段落误判为上移，例如 `` \(a\)\n  `b\nc` ``。

两例都已加为回归测试。其余验证见 [等号行报告](2026-11-12-math-button-equals-first.md) 的 Resolution。

codex 第 5 轮又指出三点：

- **已知的保守误报。** 链接的目标或标题跨行时，Comrak 0.54 报告的链接结束行偏早。例如段落 `\(a\)` 之后紧跟一个链接，链接的目标 `u` 与标题 `"t"` 分在两行（回归测试 `phase11b_conversion_skips_blocks_shifted_by_reference_definitions` 中有原文）。判据会把这种段落误判为上移。
  - 现在两步都只在源码含 `]:` 时检查，所以只有文中还有 `]:` 时，这一段才会被跳过。跳过不会改坏文本。
  - 已写入 plan 07 与功能说明，并加了回归测试。
  - 想区分这种情况与引用定义，就得自行解析链接语法，所以不做。
- **深层引用的平方级开销。** 第一步对每个节点都向上扫祖先。现在改为在遍历时，于进入、退出节点处维护容器状态。
- **解析次数超出 plan。** 第二步原先为了找上移块，另做了一次解析。现在这些块在 Preview 的同一次解析中取得，最坏情况下两步各解析两次，与 plan 一致。

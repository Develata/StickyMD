# RISK：注销时 launchd 结束仍在运行的 StickyMD（2026-11-12）

## 结论

`09` 规定 macOS 的系统终止请求（注销、关机）走共享退出屏障。实测注销时，这条路径只成立一半：

- **退出请求会到，但不被等待。** loginwindow 向 StickyMD 发退出 Apple Event，退出屏障会运行。但 StickyMD 是 UI Element 应用（没有 Dock 图标，见 W01），不在普通应用的退出列表里。loginwindow 要等过了不可撤销点才给它发这个请求，而且不等回复。所以它既不能取消注销，也不能让注销等它。
- **还没退出的进程会被 SIGTERM 结束。** 用户启动的 StickyMD（Finder 或 `open`，由 launchd 托管）在退出请求发出约 1 s 后若仍在运行，launchd 会移除它的服务，进程随即被 SIGTERM 结束（证据 3）。产品不处理 SIGTERM，默认处置立即结束进程，屏障也就到此为止。

后果：

- 探针里笔记是干净的，屏障从处理退出事件到回复只用了几十毫秒（证据 3），赶在 SIGTERM 之前。有未保存文本、笔记很大或有资产事务时要多久，没有测。
- 屏障若超过约 1 s（例如笔记很大、磁盘慢，或资产粘贴事务尚未收敛），尚未落盘的编辑会丢失。原子替换保证磁盘上不会出现写了一半的文件。
- 保存失败时，回 `NO` 拦不住注销。进程被 SIGTERM 结束，用户看不到“退出已取消：保存失败”。这一点任何方案都改变不了，最多是在被强制结束前多给屏障一些时间。
- 导出对话框打开时注销照常完成（证据 1），`09` 所说的“这次注销被中断一次”不成立。这次没有观察到对话框是否按取消结束、屏障是否完成：驱动随后就被中止了。

只影响 macOS 宿主。关机未实测，推断走同一套流程。

## 对验收的影响

- P16-W12 记为 `BLOCKED`：注销这一部分与 `09` 不符，屏障可能被 SIGTERM 截断，“这次注销被中断一次”也不成立。原因不在测试工具。
- 驱动不驱动真实注销，因为注销会结束驱动。方案 A 实施后，可以向产品进程直接发 SIGTERM 来验证保存与退出；真实注销仍用 SSH 探针另测，探针所在的 SSH 会话在注销后仍然存活。

## Resolution：方案 A 已实施（2026-11-12）

### 决定

- USER 先在本报告的初版上批准了方案 A（“按方案 A 修”）。初版没有推送，它误读了证据 2 的日志：只看到普通应用的退出列表跳过 StickyMD，漏看了第 947 行起发给它的退出事件，于是把机制写成“loginwindow 不请求 UI Element 应用退出，而以 SIGTERM 结束进程”。按初版实施并在 VM 复跑之后，补做的注销探针（证据 3）推翻了这个前提。
- 更正之后，USER 选择回到推送前的提交重做：本报告与相关提交按实测机制重写，方案 A 的做法不变。USER 同时批准了 `09`“系统终止”行的新措辞，并保留 5 s 期限（2026-11-12）。

### 实现

- `apps/stickymd-mac/src/platform/macos/sigterm.rs`：在主队列上建立 SIGTERM 的 libdispatch 信号源。信号源注册完成后才把 SIGTERM 的处置改为忽略；注册完成前 SIGTERM 仍按默认处置结束进程，所以不会有被忽略却没有送达的 SIGTERM。安装成功后，再调用不做任何事。
- `app.rs` 的 `quit_requested_by_signal`：有模态窗口时先 `abortModal`（导出按取消处理），再投递与托盘“退出”相同的退出意图，走共享退出屏障。SIGTERM 没有回复要发。
- 期限：SIGTERM 发起的退出期限为 5 s。每次退出只设一次，重复的 SIGTERM 不会推迟它；系统退出请求已经设了期限时不另设；退出结束（成功或放弃）时撤销。注销时 SIGKILL 先到（见下节），所以这个期限约束的是没有 SIGKILL 跟进的 SIGTERM，例如手动 `kill`。
- `09` 映射表“系统终止”行按 USER 批准的措辞改写，删去了“这次注销被中断一次”。`09` 的整篇摘要随之更新；Windows 人工条款绑定的各节摘要都没有变。共享层与 Windows 未改动，不需要 Windows 回归。

### 测量：进程冻住时注销会怎样

探针 `logout-probe5.sh` 与证据 3 的 probe4 相同，只是把 SIGCONT 推迟到 50 s，好看清进程被强制结束之前发生了什么。两个实例都在注销请求前 SIGSTOP。

| 构建 | `open` 实例：退出事件 → launchd 移除服务 → 结束 | SSH 实例 |
| --- | --- | --- |
| 修复前 `a00d2148…`（probe4，`logout-probe-stopped/`） | pid 760：19:06:06.780 → 19:06:07.926（+1.15 s）→ 19:06:08.030 `(2, 15, 15)`，被 SIGTERM 结束 | 没有被结束 |
| 中间构建 `a943e45b…`（`logout-probe-stopped-fixed/`） | pid 742：05:19:25.663 → 05:19:26.683（+1.02 s）→ 05:19:27.686 `(2, 9, 9)`（移除服务后 1.003 s），被 SIGKILL 结束 | pid 738：没有被结束；SIGCONT 后处理退出事件并退出 |
| 本次构建 `4e19774d…`（`logout-probe-stopped-redo/`） | pid 2318：07:32:30.093 → 07:32:33.093（+3.00 s）→ 07:32:34.100 `(2, 9, 9)`（移除服务后 1.007 s），被 SIGKILL 结束 | pid 2317：没有被结束；SIGCONT 后 07:33:21.657 处理退出事件，07:33:21.662 回复 `YES`，然后退出 |

中间构建是重做前的修复提交构建的，与本次构建只差两条 stderr 文本和注释。

结论：

- 修复后，SIGTERM 不再结束进程，进程一直活到 SIGKILL。两次样本中，SIGKILL 都在移除服务后约 1.0 s 到来。
- 从退出事件到移除服务，三次样本分别是 1.15 s、1.02 s、3.00 s。本报告结论里的“约 1 s”只是前两次；实际是 1 到 3 s，而且会变。
- 日志没有直接记下 SIGTERM 与 SIGKILL 的发出时刻，只记了服务移除和死亡原因。“移除服务时发 SIGTERM”是推断。
- 进程冻住时什么都不能执行，所以这个探针测不到 5 s 期限，也证明不了多出来的约 1 s 足够完成一次慢保存。
- `09` 的行仍用 USER 批准的措辞（“约 1 s 后发 SIGKILL”），与这两次样本一致。

### 残留（审查第 8 轮，已核实，不修）

期限到时，宿主投递一个“期限已到”事件，这个事件不带退出的身份。如果它已经投递、还没被处理，这次退出就结束了，而紧接着又开始一次新的退出，那么这个旧事件会按超时处理新的退出：

- 笔记尚未安全时，退出被取消，提示超时；
- 笔记已安全时，跳过剩余的尽力项直接退出。

两种结果都不会丢数据。窗口很窄，需要两次退出在同一个事件间隙内衔接。要修，得在共享的 `HostSignal` 里加上退出的身份；这会改动共享层，所以没有修。

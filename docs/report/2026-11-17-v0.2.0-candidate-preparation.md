## 分工

- **macOS 会话（本记录作者）：** 发布准备提交（版本号、发布说明、本记录），本机检查，推送 main，核验该 source 的 CI，触发候选构建，
  晋升操作的 dispatch 与公开附件核验。
- **Windows 会话（资格化 clone）：** 在同一 exact source 上建立 Source Freeze 并记录 `RELEASE-VERSION` 决定，按 run/attempt 下载、
  校验并 Promote 候选，运行 `qualification modules` 与需要重跑的模块，给出 readiness 与人工项清单。
  动态收据留在 Windows clone 的 ignored `dist/evidence/`，不回写本记录制造事后通过。

## 版本号

workspace 版本 `0.1.3` → `0.2.0`。0.x 语义下 `^0.1.0` 不接受 `0.2.0`，所以各 crate 对内部 crate 的 `version = "0.1.0"` 一并改为 `0.2.0`；
`Cargo.lock` 只更新八个工作区包的版本，外部依赖不变。

## macOS 构建的验收身份

Phase 16 的 `mac-gui` 账本 PASS 与人工收据绑定 app 可执行文件的 SHA-256（plan 11 #phase-16-macos-host）。改版本号后 0.2.0 构建的哈希不同，
这些记录对它不成立，本次也不在 `mac-test` 虚拟机重跑。发布说明如实写明：macOS 版从本版本源码本机构建，0.2.0 构建的验收没有重跑。

USER 认为以可执行文件哈希为锚点的做法有问题，建议改用提交或其他锚点。这属于验收流程的骨架改动，另写分析报告请 USER 决定，不在本次发布中改动。

## 失败路径

- CI、来源、包校验或原生运行库失败：保留日志并定位，不以重建另一个包替代已校验字节。
- 必要的源码修复产生新的 Source Freeze 与候选；本记录的授权随之重新绑定，tag 不移动、不覆盖。
- 缺少目标环境或人工观察：如实保留 `NOT TESTED`，不改写为通过。

本记录不修改 plan、依赖、产品架构、预算或验证阈值。准备内容遵循[发布清单](../release-checklist.md)与
[plan 11](../plan/11_testing_and_release.md#release-artifact-authority)。

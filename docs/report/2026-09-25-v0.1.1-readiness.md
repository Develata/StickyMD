## 背景与范围

## 问题与复现

readiness 的候选版本判断硬编码为 `0.1.0`，与未来版本应绑定当前 Source Freeze 的合同冲突。
此外，每次 Freeze 从 Phase 12 历史模板投影决策时，会把旧版的 `RELEASE-VERSION`
批准状态直接带入新版本，缺少重新记录当前版本授权的步骤。

加入两项回归后，在保留原判定的代码上运行
`cargo test -p stickymd-smoke --locked --bin stickymd-smoke version_`：6 项通过，2 项失败。
`0.1.1` 被误报为应使用 `0.1.0`；新 Freeze 的版本决定仍为 `USER APPROVED`，而非 `PENDING`。
日志为 ignored `dist/evidence/v0.1.1-release/version-regression-before.log`。

## 修复与验证

- 候选 source、lock hash、version 与当前 Source Freeze 统一核对；旧版本不匹配仍拒绝。
- 每次投影将 `RELEASE-VERSION` 初始化为 `PENDING`；随后由既有 decision CLI 记录本次明确授权。
- 保留 artifact、模块指纹、人工验收、独立 TAG/DRAFT/PUBLISH authority 等全部既有检查。
- `cargo test -p stickymd-smoke --locked --bin stickymd-smoke qualification::`：46 项通过，0 失败。
  日志为 ignored `dist/evidence/v0.1.1-release/qualification-regression-after.log`。

将常量直接替换为 `0.1.1` 会在下次发布重现同一问题；取消版本校验又会破坏身份边界。
当前修复使用已有 Source Freeze 和 decision receipt，不增加新权威或修改工程骨架。

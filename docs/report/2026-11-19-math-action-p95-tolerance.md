# 公式按钮性能检查的采样容错（2026-11-19）

## 背景

2026-11-18 `main` 的 CI run `44358858663`（提交 `07204e6`，只改文档）在 Windows 性能任务失败：
`crates/stickymd-render/src/math_action.rs` 的 `phase11b_performance_math_action_one_mib` 测得
p95 52.7 ms，超过 [plan 07](../plan/07_editor_and_ime.md) 的 `< 50 ms`（中位数 30.9 ms，最大 63.9 ms）。
下一个提交 `7e2cdeb` 上同一测试 p95 28.3 ms，通过。

当时的做法：不预热，计时 25 次，p95 取 `samples[n * 95 / 100]`，即排序后第 24 个。只要 2 个样本超过
50 ms 就判失败。

## 判断

- 已核实：中位数在各轮之间相差近一倍（16.7–31.5 ms），但它与 `parse` 的比值稳定在 1.21–1.45，
  所以这部分差别来自分到的机器快慢。失败那轮的比值是 1.29，属于正常范围：不是代码回归，也不是整台机器
  偏慢。
- 推断（日志只有汇总，没有逐个样本）：`07204e6` 与 `fc97e83` 两轮的 p95/中位数明显偏高，各有约 2 个
  样本偏慢，形态像共享主机的短暂卡顿。`fc97e83` 的机器快，没有越线。

## 可选路径

| 方案 | 2–3 个样本卡顿 | 整台机器更慢 | 规格改动 |
| --- | --- | --- | --- |
| A. 预热、增加样本、门槛不变 | 容得下（最多 5 个） | 仍失败（属真实信号） | 写明采样做法 |
| B. 门槛提高到 75 ms | 容得下 | 余量约为目前最慢 p95 的 2 倍 | 改门槛数值；快机器上约 3 倍的退化也能通过 |
| C. 与同一轮解析时间比较，50 ms 只记录 | 部分容得下 | 容得下 | 改检查的定义 |

失败后自动重测未列入：plan 11 规定，performance hard gate 不适用成功率容错。

## 对规格的影响

plan 07 的门槛数值与"超过时先审计"的处置不变，只补写采样做法与容错数量；验收投影同步。不涉及骨架。

## USER 决定（2026-11-19）

提高容错数量，门槛仍为 `< 50 ms`。新做法写入 plan 07 与
[`phase-11-b` 验收投影](../acceptance-cases/phase-11-b.md)：

- 先不计时运行 3 次，再计时 100 次；
- 取 nearest-rank p95，即排序后第 95 个样本，因此最多 5 个样本可以超出；
- 样本按运行顺序打印（`samples_ms=[…]`），汇总行格式不变。
- 每次计时点击前，先计时一次同一文档的单次 Comrak 解析，打印两者中位数之比（`median_over_parse`），
  只作诊断。原因：本机比 Windows CI 快约 3 倍，绝对门槛在本机放过了"每次处理复制全文 1000 次"这种
  退化（中位数 32.8 ms），而同一实验中比值从约 7 升到 22.8。USER 选定以同一文档的解析作测速基准；
  比值门槛的数值等拿到 Windows CI 基线后再定，届时再改 plan 07。

测试的 `summary` 改为 nearest-rank（第 ⌈0.95 n⌉ 个）。原写法在 n = 100 时会取第 96 个；对 n = 25 与
同文件 9 样本的线性测试，取位不变。

## 验证

在 `7e2cdeb` 加本改动、Apple 芯片 macOS 上执行：

```text
cargo test -p stickymd-render --release --locked --lib phase11b_performance_ -- --ignored --nocapture --test-threads=1
```

三项 `phase11b_performance_` 都通过。按钮的中位数 8.9 ms、p95 9.7 ms、最大 11.1 ms，100 个样本按顺序
打印。

随后向 `run_math_action` 临时注入以下改动，逐项运行同一测试（检验后已撤除，`git diff` 无残留）：

| 注入 | 结果 |
| --- | --- |
| 每次处理复制全文 5000 次（每次点击都变慢） | FAILED：中位数 93.3 ms，p95 110.6 ms |
| 第 10–12 个计时样本各多等 60 ms（3 个卡顿） | 通过：p95 10.2 ms，最大 73.2 ms |
| 第 10–14 个（5 个卡顿） | 通过：p95 9.6 ms |
| 第 10–15 个（6 个卡顿） | FAILED：p95 68.9 ms |
| 每次处理复制全文 1000 次 | 本机通过：中位数 26.2 ms |

最后一行说明，在快机器上，绝对门槛对约 3 倍的退化不敏感。这是改动前就有的性质，与本次容错无关。

CI 的 Phase 11-B Release 基线任务执行的就是上面这条命令（`stickymd-smoke modules run render
--mode=performance --plan` 列出），只按退出码判定，新增的 `samples_ms` 行不影响它。完整的
`stickymd-smoke phase 11-b --performance` 要求 Windows 验收环境，本机未运行。

`semantic_conversion.rs` 的 `phase11b_performance_one_mib_with_one_thousand_math_nodes` 只测第二步，仍为
25 个样本、p95 `< 50 ms`。它不是 plan 07 这句所指的检查（那句说的是含提交前再次处理的整个按钮），
CI 上 p95 为 2–4 ms，未改。

Windows CI 上的新做法：`NOT TESTED`，以推送后第一次 CI 为准。

## 局限

- 容许超出的比例几乎没变：旧做法 25 个中 1 个（4%），新做法 100 个中 5 个（5%），但计时窗口约长 4 倍
  （CI 上约 3 s）。收益在于一次卡顿只要波及不超过 5 个样本就不再失败；3 s 内出现两次各 3 个样本的卡顿，
  或一次超过约 150 ms 的卡顿，仍会失败。
- 本地注入只证明计数规则（5 个通过、6 个失败），不证明 Windows 上的偶发失败会减少。
- 如果慢样本不是成串出现，而是各自独立出现，按二项分布估算：每个样本有 2% 的概率偏慢时，旧做法约
  8.9% 的运行会失败，新做法约 1.5%；概率为 3% 时分别约 17% 与 8%。这是模型推算，不是实测。
- 整台机器慢到中位数接近 50 ms 时仍会失败。这正是 plan 07 要抓的信号，不属于噪声。
- 之后的 Windows CI 会打出逐个样本，可以据此判断卡顿是成串还是零散；若仍频繁失败，再评估提高门槛，
  或改为与同一轮解析时间比较。

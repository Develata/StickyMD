**范围**是 `v0.2.0..R`，包括：

## 发布提交 R 与构建来源

- **R** 是 `main` 上带着本记录与发布说明的那个提交（本记录所在 PR 的合并提交）。合并之后，R 的 SHA 在下文的 Resolution 中写明。
- **构建来源 S：** 两个平台都在 R 上构建（S = R），本版本不沿用祖先提交上的构建。之后若只有一个平台需要修复而重建，另一个平台按
  `11` #platform-artifact-reuse 判定能否沿用。沿用判定在干净的 R 检出上运行；构建缓存的前提见 `11` #macos-readiness-check“USER 2026-11-26
  增补的前提”。
- **R 之后对矩阵的改动：** 冻结 R 之后，`docs/plan/` 或 `docs/acceptance-cases/` 下的任何改动都会使 Windows 全部资格化模块的收据失效
  （`11` #module-success-ledger）。所以每版的 macOS 发布证据只记在本记录与 ignored 的 `dist/evidence/` 下，不写进验收矩阵（`11` Phase 18 节）。

## 尚未取得、须逐项授权的操作

“开始写”只授权写本记录与发布说明。以下每一项都要 USER 在当时单独授权：

1. 推送本记录所在的分支、开 PR，以及合并它；合并的结果即 R。
2. 对 R 各触发一次 candidate-only 的 `release.yml`（Windows）与 `release-macos.yml`（macOS）。
3. `mac-test` 虚拟机中的运行：`mac-gui`（含 R03 的 `--zip` 候选包运行）、`mac-resources`、三次 `mac-logout`。虚拟机只在 Develata 说明在键盘前时启动。
4. 真实下载路径 P18-D01–D05。这是第一个公开的 macOS 包，这一项本版不可 waiver。浏览器下载、访达中的移动、Gatekeeper 的放行、口令与 SSH 登录，都是 Develata 的步骤。
5. 人工行的发布用 USER 收据或 waiver（`mac-ledger receipt|waive --release-source <R> --candidate-sha256 <摘要>`），以及 Windows 的 Tier A 与 Tier B 人工项。
6. TAG、DRAFT-RELEASE、PUBLISH 三项晋升操作，各自单独授权。PUBLISH 之前，仓库 ruleset 须禁止更新与删除 `refs/tags/v*`（发布清单第 6 节）。

不需要远端授权、但依赖上面某一项的本机步骤：macOS 晋升（`release macos-promote`，依赖第 2 项的 artifact）、R 上的源码测试、`mac-ledger record` 与 `macos-ready`。

**前提：** Windows 一侧要有一个能在 R 上建立 Source Freeze、跑资格化模块与人工项的 Windows 会话。它是否、何时在线由 USER 安排；没有它，Windows readiness 不能成立，整个版本不发布。

## 分工

- **macOS 会话：**
  - 本记录与发布说明；
  - 推送与 CI 核验；
  - 两个候选 workflow 的触发；
  - macOS 晋升；
  - R 上的源码测试；
  - 虚拟机运行与账本登记；
  - `macos-ready`；
  - TAG、DRAFT、PUBLISH 的触发与公开附件的核验。
- **Windows 会话（资格化 clone）：**
  - 在 R 上建立 Source Freeze，记录 `RELEASE-VERSION` 决定；
  - 按 run 与 attempt 下载、校验并 Promote Windows 候选；
  - 运行 `qualification modules` 与需要重跑的模块；
  - 给出 readiness 与人工项清单。

  动态收据留在 Windows clone 的 ignored `dist/evidence/`。由于 `docs/plan/` 与 `docs/acceptance-cases/` 自 v0.2.0 以来都改过，Windows 全部资格化模块都要在 R 上重跑。

## macOS 的验证顺序

按 `11` #macos-readiness-check，后一步用到前一步的结果：

1. 在干净的 R 检出上晋升 macOS 候选，写下候选 receipt 与晋升复核记录；
2. 在 R 上运行源码测试，它同时构建 R 的 `mac-gui` 驱动（`target/macos-driver/release/stickymd-smoke`）；
3. 在 `mac-test` 中，用这个驱动在晋升出的 bundle 上运行 `mac-gui`（R03 以 `--zip` 打开候选 ZIP，给一个批次名）、`mac-resources` 与三次 `mac-logout`；
4. 在主机上以 `mac-ledger record` 登记这些运行的证据；
5. `release macos-candidate --release-source <R>` 打印候选 receipt 的摘要，USER 照抄它登记发布用收据、waiver 与下载记录；
6. `release macos-ready --release-source <R> --macos-major 27 --driver <R 的驱动> --batch <批次>`，逐行判定。

Windows 一侧的顺序见发布清单第 1–5 节。

## 失败路径

- **构建或校验失败：** CI、来源、包校验、签名观察或原生运行库失败时，保留日志并定位，不以重建另一个包替代已校验的字节。
- **必要的源码修复：** 产生新的 R 与新的候选，本记录中待授权的操作随之重新绑定。tag 不移动、不覆盖。
  只修一个平台时，另一个平台按 #platform-artifact-reuse 判定能否沿用，并在新的 R 上重跑受影响的门。
- **缺少目标环境或人工观察：** 如实保留 `NOT TESTED`，或在 USER 逐行 waiver 之后记为 `WAIVED`，不改写为通过。

本记录不修改 plan、依赖、产品架构、预算或验证阈值。准备内容遵循[发布清单](../release-checklist.md)与
[plan 11](../plan/11_testing_and_release.md#release-artifact-authority)。

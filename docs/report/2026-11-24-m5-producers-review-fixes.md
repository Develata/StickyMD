## 需要 Develata 决定

（USER 2026-11-24 已选 A，在叠加分支 `feat/m5-view-diagnostic` 上实现，另开 PR；本分支保持下述 fail closed。）

**F7：怎样确认资源测量的每个场景确实以所配置的视图打开。** `mac-resources` 给 Source、Preview、Split 三个场景写不同的 `view_mode`，
但只确认产品进程有一个足够大的窗口。产品若忽略配置，三组 Source 的测量会被当作三个场景计数；Preview 与 Split 的内存门更宽，忽略配置只会让
R01 更容易通过。现有手段都证明不了视图：主窗口是自绘的，没有辅助功能元素；菜单栏菜单只有“隐藏”“置顶”“退出”三项；启动时的窗口几何最多
区分 Split，分不开 Source 与 Preview；源码测试证明的是“配置决定启动视图”的逻辑，不是这一次运行真的读到了这份配置。

**在你决定之前（已实现，fail closed）：** R01、R02 都不判 PASS。运行完整、读数都在门内时，这一行记为 `NOT_TESTED`，原因写明“没有运行确认它的场景以所配置的视图打开”；
`FAIL` 照常记为 `FAIL`。`mac-resources` 在这种情况下仍以 0 退出，表示测量本身成立。账本照此登记，发布门对这两行判 `NOT_TESTED`，可由你 waiver。

| 办法 | 做法 | 代价与风险 | R01、R02 能否 PASS |
| --- | --- | --- | --- |
| A（建议）产品的诊断报告 | 仿照现有的 `STICKYMD_DIAGNOSTIC_INPUT_LATENCY`：设置一个默认关闭的诊断环境变量时，macOS 宿主在窗口就绪后写一个小文件，记下 Shared Desktop 当前显示的视图与窗口尺寸。`mac-resources` 每次运行都设这个变量，在预热之前读这个文件并写进证据；只有报告的视图等于场景所配置视图的运行才算有效 | 改产品代码（只在宿主的诊断路径，默认关闭，不改用户可见行为），需要你批准，并写进 `09`/`10` 的诊断条款；产品输入指纹随之改变（下一版本本来就要重建）。报告的是 shell 认定的视图，不是像素，但要排除的正是“配置没有生效”，这正是 shell 的状态 | 能。实现并在虚拟机中用一个故意配错视图的坏样本验证之后，完整且在门内的运行即为 PASS |

### 需要 Develata 决定：R03 的“不写文件”（B9）

现行条款（plan 11 #macos-release-gate 的 R03 行）是“所观察的目录不写文件”，而且不可 waiver。两次快照只能证明“结束时所列属性与开始时相同”：
产品在运行中写入后又复原（连时间一起）、或只改权限与扩展属性，快照都看不出。在你决定之前，这一项记为 `NOT TESTED`，所以 R03 不能为 PASS，
发布门不成立。

| 办法 | 做法 | 代价与风险 | R03 能否 PASS |
| --- | --- | --- | --- |
| A（建议）kqueue 写入观测 | 启动前，对被观察文件夹中的每个文件与文件夹以 `O_EVTONLY` 打开，在 kqueue 上登记 `EVFILT_VNODE`（写、扩展、链接、改名、删除），运行结束后读出全部事件。kqueue 对每个登记对象保留“发生过”的标志，事件会合并但不会丢；登记失败或观测中断时为 `NOT_TESTED`。另做“写后复原”的对照坏样本。权限与扩展属性的变化（`NOTE_ATTRIB`）不计入“写文件”，因为 Gatekeeper 自己会改 bundle 的隔离属性 | 驱动里多一段原生代码（`unsafe`，放在 `mac_gui/native`），需要在虚拟机中确认系统自己不会触发写入事件；不改合同的措辞 | 能，实现并在虚拟机中用坏样本验证之后 |
| B 改写条款 | 把 R03 的这一项改成快照实际能证明的“结束时所列属性与开始时相同” | 改动 USER 批准过的发布门措辞；运行中写入后复原的情况从此不在门内 | 能，现在即可 |
| C FSEvents | 用 FSEvents 观测这棵树，并以 `kFSEventStreamEventFlagMustScanSubDirs` 等标志识别事件丢失，丢失时为 `NOT_TESTED` | 苹果文档说明事件会合并、也可能丢失；丢失时只能判 `NOT_TESTED`，在繁忙的系统上可能常常判不了 | 能，但可能常为 `NOT_TESTED` |

建议 A：它不改合同，对“运行中写入后复原”这一反例有确定的答案，而且观测本身不会丢失“写过”的事实。

### 需要 Develata 决定：R02 的 60 s 窗口（B3）

`10` 的硬门是“60 s 平均 > 0.1%”。驱动在第一次采样之后睡 60 s 再采第二次，第二次总会晚到一点（虚拟机里至多 20 ms，允许 0.5 s）。两次采样之间的 CPU 时间不超过 60 ms 时，其中任一个 60 s 窗口都不超过硬门，所以“成立”可以证明；但窗口长于 60 s 时，两次采样说不出 CPU 花在哪一段，不能证明有某个 60 s 窗口超过。现在的过渡规则因此只在窗口恰为 60 s 时判 FAIL；实际运行几乎总是晚到，所以超过硬门的场景在过渡规则下只能为 `NOT TESTED`，而 R02 的 `NOT TESTED` 可以 waiver。

| 办法 | 做法 | 代价与风险 |
| --- | --- | --- |
| A（建议）第三次采样 | 在 60 s 之前（例如 59.9 s）再采一次。下界取自它（不到 60 s 的窗口中的 CPU 不多于这个 60 s 窗口），上界取自 60 s 之后那次。超过下界即 FAIL，不超过上界即成立，只剩两次采样之间约 0.1–0.5 s 的 CPU 无法判定 | 驱动、读器与证据格式（schema 6）都要改，`mac-resources` 要在虚拟机中重跑；视图诊断分支的 schema 顺延 |
| B 记录 CPU 核数 | 下界取 C − 核数 × (W − 60)，不改采样 | 晚到 20 ms、4 核时，C 超过 140 ms（硬门的两倍多）才判 FAIL，略超硬门的场景仍为 `NOT TESTED` |
| C 改条款 | 硬门改为“所测窗口（60–60.5 s）的平均” | 改动 `10` 与 `11` 的措辞，偏离“60 s 平均”至多 0.8%；判定回到第二轮的做法 |

建议 A：它不改条款，成立与 FAIL 都有证明，剩下的无法判定区间很窄。

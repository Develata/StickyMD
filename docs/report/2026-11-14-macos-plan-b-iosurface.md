# 评估：macOS 方案 B，用 IOSurface 直接呈现（2026-11-14）

## 结论

**建议批准方案 B 进入正式实现。** 原型在 VM 里同时改善了延迟和内存：

- **按键延迟：** 持续输入时每帧绘制的中位数从约 8.7 ms 降到约 3.5 ms；空闲后首键从 13–18 ms 降到约 5–6 ms。
- **常驻内存：** Source/Preview/Split 每种约少 10.7 MiB，Hidden 不变。
- **回归：** `mac-gui` 自动化行与上一轮相同。

**前提：** 原型只在 VM 里测过，像素是否正确（颜色、方向、是否撕裂）还没有人看过。需要 USER 先在本机看一眼原型（见文末）。

**性质：** 这是呈现边界的改动，属于骨架级，须 USER 批准后才进入正式实现。正式实现要改 `03`、`06`、`09`、`10` 四章。

## 背景

[内存报告](2026-11-13-macos-memory-optimization.md) 的末两节已经说明：

- 每键绘制在 VM 里 66–70% 的时间花在 CoreAnimation 把 softbuffer 0.4.8 交来的 CGImage 整帧再渲染、复制一遍上；
- 这份复制同时留下一份常驻的 5.4 MiB 副本；
- softbuffer 每次 present 还要新分配一块整帧缓冲；
- 把 IOSurface 直接作为图层内容，系统就不必复制。上游 softbuffer 的 IOSurface PR #329 尚未合并。

USER 2026-11-13 要求“做原型和报告”。

## 原型

**位置：** 分支 `proto/iosurface-presenter`，提交 `3a3f7ef`，基于 `feat/macos-host` 的 `4f811b1`。这是评估用的原型，不进产品分支。

**做法：**

- **宿主自己呈现。** 共享层的 `Host` 加了一个默认返回 `None` 的 `present_frame`。macOS 宿主实现它，Windows 走原来的 softbuffer。
- **IOSurface 轮换。** macOS 宿主在 `platform/macos/iosurface.rs` 里维护最多 4 个 BGRA 格式的 IOSurface：
  - 每帧挑一个系统没在用（`IOSurfaceIsInUse` 为假）、也不是当前图层内容的；
  - 加锁，把 tiny-skia 画布的 RGBA 转成 BGRA 写进去，解锁；
  - 在禁用动画的事务里把它设为一个子图层的内容。
- **图层几何沿用 softbuffer 的设置：** 锚点 (0,0)，`geometryFlipped`，左上对齐，不透明；每帧同步根图层的 bounds 和缩放。
- **绕开 softbuffer：** 不再调用 softbuffer 的 present，它的每帧分配和 CoreAnimation 的复制随之消失。
- **隐藏：** 隐藏回执后释放全部 IOSurface，并清空图层内容。

**没做的：**

- IOSurface 的色彩空间：没有设置，softbuffer 用的是 deviceRGB；
- 局部提交；
- 直接画进 IOSurface（画布仍是一份独立的 5.4 MiB）；
- 4 个都在用时，原型会复用最旧的一个，可能撕裂，也没有计数。

## 未验证与风险

- **像素正确性：** 颜色、上下方向、打字和滚动时有没有撕裂或闪烁，都没有看过。VM 里没有屏幕录制权限，`mac-gui` 只查窗口状态和笔记内容。
- **色彩空间：** 原型的 IOSurface 没有设色彩空间，与现在的 deviceRGB 可能有细微色差。
- **撕裂：** 4 个都在用时原型会写其中最旧的一个，可能撕裂，且没有计数。
- **缓冲个数不定：** 内存因此在 2 到 3 帧之间变动。
- **未覆盖的环境：** 多显示器与混合 DPI、拖动缩放、真机（VM 的图形是半虚拟化的）都没有测。
- **这是未公开用法：** 用 IOSurface 作 `CALayer.contents` 并没有公开文档，但浏览器、GTK 和 softbuffer 的 PR #329 都这样用。

## 正式实现的设计（待批准）

1. **呈现边界。**
   - 共享层的 `Host` 增加宿主呈现能力：宿主拿到完成的画布，自己负责提交；返回 `None` 时仍走 softbuffer。
   - macOS 宿主实现 IOSurface 呈现器，原生调用只在 `platform/macos/` 里。
   - Windows 不实现这个能力，行为不变。
   - 共享层的绘制流程（`render.rs`）有改动，需要 Windows 回归。
2. **缓冲。**
   - 默认 3 个，用 `IOSurfaceIsInUse` 判断能否写；
   - 都在用时不写在用的缓冲：本帧跳过，下一次事件循环再画，并计数；
   - 上限写进 plan。
3. **色彩空间。** 设为与现在一致的色彩空间，先比较 deviceRGB 与 sRGB 的效果，再定。
4. **隐藏与显示。** 沿用方案 A：隐藏回执后释放全部 IOSurface，显示前重建并提交一帧。
5. **macOS 上不再创建 softbuffer 的表面。** 省掉它的子图层和逐帧分配；画布改由共享层或呈现器持有。
6. **可以另行评估的后续：**
   - tiny-skia 直接画进 IOSurface（若 RGBA 格式的 IOSurface 可用），省掉 5.4 MiB 画布和一次转换；
   - 只提交变化区域；
   - 分配器的备用块：softbuffer 不再逐帧分配后，它主要服务于其他大块分配，可以重新评估是否保留。
7. **plan 修改：**
   - `03`：呈现所有权；
   - `06` frame-presentation：macOS 的呈现路径；
   - `09` macOS 映射：图层与缓冲生命周期；
   - `10` macOS 门：内存策略与延迟诊断的结论。
8. **验证：**
   - 单元测试，覆盖缓冲选择与释放；
   - `mac-latency` 的 A/B；
   - `mac-resources` 跑 5 次；
   - `mac-gui`；
   - USER 目视；
   - Windows 桌面回归；
   - codex-reviewer 审查。

## 复核与更正（2026-11-14，codex-reviewer）

codex 只读复核了本报告、原型 `3a3f7ef` 和证据：

- **数字全部复算一致：** 延迟原始日志、逐轮与合并统计、资源 JSON 的中位与最大值、分区拆解里的表面个数、`mac-gui` 逐行结果、全部哈希。
- **边界可以认可：** 宿主提供呈现能力、原生调用留在平台目录、Windows 保留原后端。

它给出的阻断项都在原型代码里，正式实现必须改掉，都已核实：

1. **IOSurface 创建失败会崩溃。** `iosurface.rs:83` 的 `then_some(Self(surface))` 会先构造对象，创建失败时等于对空指针调用 `CFRelease`。
2. **全忙时会写正在使用的缓冲。** 达到 4 个后，原型直接取第一个非前台的缓冲，不再检查是否在用，也不是“最旧”的，因而可能撕裂。测量期间是否走过这条路径没有计数，无法排除。
3. **原生光标失败后，降级的光标闪烁提交到了 softbuffer 的图层。** 那条路径不经过新的呈现入口，而上面的 IOSurface 图层盖住了它。

**对上文的更正：**

- **“A/A 波动之外”说过头了。** A/A 单次运行的绘制 p50 跨度，持续输入约 5.4 ms，空闲后首键约 11–12 ms。本次 1 MiB 持续输入中，最慢的原型（3.89 ms）与最快的基线（4.41 ms）只差 0.5 ms。准确的说法是：本次四个场景里，原型每一轮都快于基线每一轮。精确的稳定收益尚未确定，若要显著性结论，须以运行为独立样本，平衡顺序复测。
- **“总延迟”的终点是 present 返回。** 它不含合成与显示。换了呈现方式后，这个终点之前包含的工作也变了，所以只能证明主线程更早返回，不能证明像素同幅度更早上屏。真实的输入到屏幕延迟待验证。
- **内存范围漏了一个反例。** 探针里“隐藏后再显示”的 Source 是 48.2 MiB（3 个表面加重建）。原型的池上限是 4 个，池增长后也不会缩回。2 或 3 个只是这几次的观察，不是上界。正式的池策略要重新测量。
- **与 r11 的比较是参考性的。** “关闭的延迟记录器不影响内存”只是假设。精确的内存收益要用本次基线 `fdbd90ef…` 与修复后的原型，在同一批次、同一驱动下交替测量。
- **IOSurface 作图层内容是公开支持的。** SDK 的 `CALayer.h` 写明 `contents` 一般是 CGImageRef 或 IOSurfaceRef，WWDC23 也讲过这种用法。上文“没有公开文档”是错的。真正的风险在像素格式、色彩、复用时序和系统版本行为上。
- **色彩空间的风险被低估了。** deviceRGB 依赖设备，不能默认与 sRGB 等价，差异也不一定“细微”。正式实现要通过 `kIOSurfaceColorSpace` 明确设定，先证明与现状等价，再考虑改变。
- **Hidden 的“已拥有、未映射”约 5.5 MiB 已核实。** “合成器拿着最后一块”仍是推断，要验证多次隐藏与显示后是否累积。

**正式设计还要补的：**

- **提交结果分三种：** 已提交、暂缓、失败。
  - 暂缓时保留最新的完整重绘请求，有界地再唤醒一次，隐藏时取消；
  - 只有真正提交才算成功，才走 `after_present` 和光标同步；
  - 换尺寸时，新资源准备好之后再替换旧内容。
- **光标降级路径也经过宿主呈现入口。**
- **几何同步：** 明确由谁负责与根图层同步（softbuffer 用观察者）。跨屏、实时缩放、失焦时继续绘制、快速隐藏与显示都要验证，并记录表面 ID、是否在用、提交与暂缓的次数。
- **除了 `03`/`06`/`09`/`10`，还要补 `11` Phase 16 的验证要求和相应的验收、smoke 与覆盖投影。**
- **替代路径仍可比较：**
  - 上游 softbuffer 的 #329：仍是草稿，允许追加缓冲，不能当作现成的上限实现；
  - tiny-skia 直接画进 IOSurface：tiny-skia 的 `PixmapMut` 没有独立的 stride 参数；
  - `CAMetalLayer`：`nextDrawable` 可能阻塞，不适合主线程低延迟路径。

**原型状态：** 原型保持测量时的样子，以对应证据。上面三个缺陷正常使用时罕见触发：创建失败、4 个缓冲全忙、原生光标失败。目视检查时若看到撕裂，可能就是第二条。

## 正式实现的复核与修复（2026-11-14，codex-reviewer）

codex 只读审查了 `git diff 435d7be 159b9b7`（模型 `gpt-6-astra`，effort `max`）。结论是没有阻断项，提了两条应修、一条可改、四条待证。逐条核实并处理如下：

1. **暂缓后再失败，旧重试仍会触发（应修，已核实）。** `render.rs` 的失败分支没清 `present_retry_at`，失败的帧会被多画一次。
   - **修复（`e1ff641`）：** 任何结果先清重试，只有暂缓才重新设置。
   - **测试：** `host_presenter_tests.rs` 新增 5 个。
     - `a_failure_after_a_deferral_ends_the_wait`：暂缓后在到期前失败，旧期限到了也不再重画。
     - `a_frame_presented_before_the_retry_is_due_ends_the_wait`：到期前提交成功，同样不再重画。
     - `a_resize_while_deferred_presents_the_new_size_once`：暂缓中改尺寸，下一帧按新尺寸提交一次。
     - `only_a_presented_frame_touches_the_caret_overlay`：暂缓和失败都不碰原生光标，只有提交成功才碰。
     - `a_show_whose_frame_fails_reports_it_and_waits_for_no_retry`：再显示时提交失败，报告诊断，不挂重试。
   - **反证：** 去掉这行清除，前三个测试失败。
2. **色彩空间设置失败仍当作成功（应修，已核实）。** 原 `set_device_rgb` 遇空就返回，表面照常使用。
   - **修复（`e1ff641`）：** `Surface::new` 返回失败原因，这一帧报告为失败，旧内容保留。
3. **deviceRGB 的序列化不能直接证明等价（待证）。** 本机上 deviceRGB 的属性表就是 sRGB。“调用同一个创建函数”本身证明不了与 softbuffer 的 deviceRGB 图像一致，这一点认可。
   - **补证（`e1ff641`）：** 单元测试 `surface_colours_match_as_device_rgb_does`，取表面上实际设置的色彩空间，与 deviceRGB 分别做颜色匹配，目标包括该空间本身和 Display P3，六个样本色（纯红、纯绿、纯蓝、中间色、浅灰、深灰）差值都小于 0.5/255。本机 macOS 27.2.1 通过。
   - **推断：** 若 CoreGraphics 把 deviceRGB 当作屏幕原生空间，匹配到 P3 时两者会不同，所以这说明颜色匹配把 deviceRGB 当 sRGB 处理。
   - **仍未验证：** 合成器实际用的是否就是这套颜色匹配，要靠 USER 在本机广色域屏上把正式新包与基线并排目视。VM 的驱动没有屏幕录制权限，不能截图比较。
4. **原生压力与失败路径没有测试（待证）。**
   - **补测（`e1ff641`）：** 呈现器改为对根图层工作，测试 `a_presenter_writes_only_free_surfaces_defers_when_none_is_free_and_lets_all_go` 在独立的 `CALayer` 上走完整个生命周期，用公开的 `IOSurfaceIncrementUseCount` 把缓冲标为“合成器在用”。测试确认：
     - 在用的缓冲不写；
     - 池满且全忙时暂缓，图层内容不变；
     - 换尺寸后池里只剩一个新缓冲；
     - 释放时清空图层内容；
     - 某个缓冲仍被占用时释放也安全，测试自己持有一个引用，模拟合成器。

5. **AX 等待的效果与等待时长没有证据（待证）。**
